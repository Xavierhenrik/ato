## Sumário Executivo

A base Flutter F1–F5 está funcional e bem estruturada para um MVP. A arquitetura de Riverpod codegen, GoRouter, Dio puro e design tokens está corretamente aplicada na maioria dos casos. Os sprints F2–F5 foram executados com consistência notável.

Entretanto, a auditoria identificou **5 bugs críticos de parsing que causam crash em produção**, **1 placeholder de tela que enganará usuários em produção** (DiagnosticoScreen), **1 ausência de declaração de fonte** que faz todo o app renderizar na fonte errada, e **3 endpoints utilizados que não constam no api-contract.md** (contrato não verificado formalmente).

Nenhuma correção foi feita nesta sessão. Este documento é o relatório completo para a sessão de correções F6-fix.

## Findings Críticos — Bloqueiam Release

### C1 — `SimuladoHistoryItem.fromJson`: crash em abandoned attempts

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/simulados/data/models/simulado_models.dart` |
| **Linha** | ~192 (campo `completedAt`) |
| **Código** | `completedAt: DateTime.parse(json['completedAt'] as String)` |
| **Problema** | `completedAt` é `null` para tentativas `abandoned` — confirmado em PROJECT_STATE.md: "POST /simulados/:id/abandon seta `status: 'abandoned'`, sem `completedAt`" |
| **Impacto** | `TypeError` (null cast to String) + crash ao abrir `/simulados` para qualquer usuário que já abandonou um simulado |
| **Fix** | `completedAt: json['completedAt'] != null ? DateTime.parse(json['completedAt'] as String) : null` — campo deve ser `DateTime?` |

---

### C2 — `Question.fromJson`: crash se `id` ausente

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/simulados/data/models/simulado_models.dart` |
| **Linha** | ~41 |
| **Código** | `id: json['id'] as String` |
| **Problema** | Cast direto sem verificação — se a API retornar um campo `id` ausente ou nulo (seja por bug ou schema mismatch), o app crasha |
| **Impacto** | Crash em `SimuladoAttemptScreen` durante qualquer simulado |
| **Fix** | `id: json['id'] as String? ?? ''` com validação ou lançar erro descritivo |

---

### C3 — `AnswerResult.fromJson`: cast sem null-check em 2 campos obrigatórios

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/simulados/data/models/simulado_models.dart` |
| **Linhas** | ~91–92 |
| **Código** | `correct: json['correct'] as bool` e `correctAnswer: json['correctAnswer'] as String` |
| **Problema** | Se o backend retornar esses campos ausentes (ex: erro 5xx mascarado como 200, ou mudança de contrato), crash imediato |
| **Impacto** | Crash após confirmar qualquer resposta no simulado |
| **Fix** | `correct: json['correct'] as bool? ?? false` e `correctAnswer: (json['correctAnswer'] ?? json['correct_answer'] ?? '') as String` |

### C4 — `DiagnosticoScreen._AnsweringState`: placeholder em produção

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/onboarding/presentation/screens/diagnostico_screen.dart` |

### C5 — `pubspec.yaml`: fonte Inter declarada em AppTextStyles mas ausente no pubspec

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `front/lcf_app/pubspec.yaml` |
| **Problema** | `AppTextStyles` usa `fontFamily: 'Inter'` em todas as definições de `TextStyle`, mas não há seção `fonts:` no pubspec.yaml declarando a fonte |
| **Impacto** | Todo o app renderiza com a fonte padrão do sistema operacional (Roboto no Android, SF Pro no iOS) em vez de Inter; toda a tipografia do design está incorreta |
| **Evidência** | `app_text_styles.dart` linhas de `bodyLarge`, `bodyMedium`, etc. usam `fontFamily: 'Inter'`; `pubspec.yaml` não contém a seção `fonts:` |
| **Fix** | Adicionar `google_fonts` ou os arquivos `.ttf` da Inter + declarar em `pubspec.yaml` → seção `fonts:` |

### I2 — `simuladoUserPlanProvider` falso negativo em network error

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/simulados/providers/simulado_provider.dart` |
| **Comportamento** | Qualquer erro (network timeout, 500) → fallback `'free'` |
| **Problema** | Um usuário PRO com rede instável tem todos os recursos PRO bloqueados pelo cliente — o gating do frontend atua erroneamente; o backend é árbitro real, mas o UX está ruim |
| **Impacto** | Usuários PRO frustrados em áreas de cobertura baixa |
| **Nota** | O comportamento foi documentado como intencional na sessão F5 ("fallback 'free' garante que o backend seja árbitro real") — mas a experiência do usuário PRO é ruim; F7 deve resolver com um provider global que usa cache |

### I3 — `simuladoHistoryProvider` não invalidado após iniciar simulado

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/simulados/presentation/screens/simulado_config_screen.dart` |
| **Linha** | `_startSimulado()` — depois de `context.push('/simulados/${attempt.id}', extra: attempt)` |
| **Problema** | Quando o usuário conclui um simulado e volta para `/simulados`, o histórico recente ainda mostra os dados antigos até o próximo hot reload / pull-to-refresh |
| **Impacto** | Stale data — o simulado recém-concluído não aparece no histórico imediatamente |
| **Fix** | `ref.invalidate(simuladoHistoryProvider)` após `context.push(...)` |

### I4 — `tutor_screen.dart`: `_onSend` só captura `DioException`

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `features/tutor/presentation/screens/tutor_screen.dart` |
| **Linha** | método `_onSend` |
| **Código** | `} on DioException catch (e) {` — bloco único |
| **Problema** | `SocketException` (sem internet), `TimeoutException` (Dio timeout global → não é DioException em todos os casos), erros de parsing (`FormatException`) propagam como exceções não tratadas para o Flutter error handler |
| **Impacto** | Crash ou black screen no chat quando há perda de conexão; revert optimista não acontece para erros não-Dio |
| **Fix** | Adicionar `} catch (e) {` genérico com SnackBar de fallback e revert do optimistic insert |

| **Arquivo** | `features/simulados/presentation/screens/simulado_config_screen.dart` |
